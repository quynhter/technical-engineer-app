# technical-engineer-app

<img src="app/itd/web_assets/logo.svg" alt="Логотип ИТД: здание" width="80" height="80">

Версия **0.6.0**.

Локальное веб-приложение для ведения исполнительной технической документации. В нём можно вести объекты и разделы, учитывать работы и материалы, выпускать акты и ведомости. ИИ-агент работает с той же базой SQLite.

Интерфейс использует Astryx 0.7.15 из `app/frontend/src`. Реестр ИД (`registry.jsx`), исходные файлы (`source-files.jsx`), списки схем/документов/ресурсов/фактов/ЖВК/ЖПК (`project-records.jsx`), работы (`work-records.jsx`), остальные таблицы ОЖР (`journal-records.jsx`), проверка/сдача (`workflow-records.jsx`) и ручное ведение (`manual-records.jsx`) работают через `/api/v1/`. Готовая сборка и действующие контроллеры native форм, версий, файлов, настроек и знаний находятся в `app/itd/web_assets`. Структура форм и таблиц исходных документов сохраняется. Старые заменённые списки и скрытая шапка удалены после проверки и подтверждений пользователя. Подробнее: [frontend](app/frontend/README.md).

## Первый запуск

Из корня проекта установите зависимости и запустите сервер. Нужен Python 3.10 или новее.

```bash
python3 -m venv .venv
.venv/bin/python -m pip install -r app/requirements.txt
.venv/bin/python -m app.itd web --no-browser
```

При первом запуске сервер создаст чистую `db/itd.db` и выведет ссылку вида `http://127.0.0.1:8765/#КОД` с кодом первого администратора. Откройте ссылку, затем укажите имя и фамилию в профиле. Сохраните код. При следующих запусках приложение показывает адрес, а войти можно по сохранённому коду или ссылке. Если адрес изменился, вставьте код на странице входа.

Для смены пароля:

```bash
.venv/bin/python - <<'PY'
from app.itd.accounts import Accounts

accounts = Accounts("db/itd.db.accounts.sqlite3")
accounts.initialize()  # Подготовить схему аккаунтов и постоянных сеансов.
admins = [user for user in accounts.list() if user["role"] == "admin"]
if len(admins) != 1:
    raise SystemExit("Для сброса нужно явно выбрать администратора.")
admin_id = admins[0]["id"]
print(accounts.rotate(admin_id, admin_id)["code"])
PY
```

Круглая кнопка с инициалами расположена справа от переключателя темы. Из профиля можно изменить имя, сменить код и выйти. После смены кода скопируйте новый из окна подтверждения. Другие сеансы этой учётной записи завершатся.

| Роль | Возможности |
| --- | --- |
| Администратор | Работа с ИТД, управление пользователями и рабочими путями |
| Редактор | Просмотр, внесение сведений, выпуск и скачивание документов |
| Наблюдатель | Просмотр сведений, предпросмотр актов и поиск по нормативам |

Администратор добавляет пользователя в профиле и передаёт ему индивидуальную ссылку или код. Изменение роли и удаление завершают действующие сеансы выбранного пользователя. Собственную роль или удаление своего аккаунта выполняет другой администратор. По умолчанию сервер слушает локальный адрес `127.0.0.1`. Учётные записи позволяют разделять доступ к одному запущенному приложению.

## Доступ по локальной сети

Остановите текущий сервер через Ctrl+C и запустите его с сетевым адресом:

```bash
.venv/bin/python -m app.itd web --host 0.0.0.0 --port 8765 --no-browser
```

На другом устройстве в той же сети откройте `http://IPv4-адрес-компьютера:8765/` и введите индивидуальный код пользователя. Например, для адреса компьютера `192.168.1.10` ссылка будет `http://192.168.1.10:8765/`. На самом сервере продолжает работать `http://127.0.0.1:8765/`. Адрес `0.0.0.0` используется только для запуска, в браузере нужен реальный IPv4-адрес компьютера. В ссылке приглашения замените `127.0.0.1` на этот адрес, сохранив порт и фрагмент после `#`.

Флаг `--host` также поддерживается в `app/scripts/start_web.py`. Вместо `0.0.0.0` можно указать IPv4-адрес конкретного интерфейса. Если выбранная БД задавалась через `--db`, сохраните этот параметр перед командой `web` при перезапуске. Если соединение блокирует межсетевой экран компьютера, разрешите входящий TCP-порт 8765 для локальной сети. Этот режим использует HTTP и предназначен для доверенной локальной сети; для доступа через интернет нужны HTTPS и отдельная настройка публикации.

## Рабочая и тестовая базы

В профиле администратора введите абсолютный путь к существующему файлу `.db` и путь к папке ИТД. Папка может быть на другом диске. Если её пока нет, приложение создаст её внутри существующего родительского каталога. Новые файлы попадут в выбранное дерево. Уже выпущенные документы и оригиналы остаются по зарегистрированным путям. Для удаления файлов через проверку папок дерево ИТД и БД должны быть на одном томе.

Чтобы подготовить чистую тестовую БД, выполните `.venv/bin/python -m app.itd --db db/test.db init`. Выделите ей отдельную папку ИТД. Приложение проверит, что её дерево не пересекается с деревом другой подключавшейся БД. Переключение рабочих путей завершает сеансы остальных пользователей и сохраняется при перезапуске. Учётные записи остаются в `db/itd.db.accounts.sqlite3` для запуска по умолчанию. Явный `--db` при запуске сервера использует отдельное хранилище настроек и учётных записей рядом с этим файлом.

## Работа с ИИ

Откройте корень проекта в агенте и передайте ему задачу и путь к используемой БД. Веб-приложение показывает справочник и работает с локальными файлами. Обработку PDF нормативов и подготовку новых шаблонов выполняет агент в чате.

- [ai-technical-engineer](skills/ai-technical-engineer/SKILL.md) ведёт ИТД от разбора исходных данных и проверки применимых требований до журналов, актов и готового комплекта. Можно поручить отдельную операцию или весь цикл. Например: «Прочитай skills/ai-technical-engineer/SKILL.md, проверь исходные данные выбранного раздела и подготовь комплект к выдаче». Укажите БД, объект, раздел и нужную стадию; реальные подписи и приёмка требуют подтверждённых оснований. Навык не содержит записей конкретных объектов.

- [construction-norm-parser](skills/construction-norm-parser/SKILL.md) преобразует нормативы в проверяемые материалы для `app/knowledge`. Индекс поиска строится из этих материалов.
- [doc-template-generator](skills/doc-template-generator/SKILL.md) подготавливает шаблоны из ваших исходных бланков. Готовые шаблоны лежат в `app/templates`, настройки полей — в `app/forms`.

Список команд доступен через `.venv/bin/python -m app.itd --help`. Если в веб-интерфейсе выбрана другая БД, передавайте её агенту явно через `--db /абсолютный/путь.db` перед подкомандой.

Просмотр списков версий, предпросмотр импорта и план файловых операций не меняют деловую БД, включая её аудит. Если карточки документа ещё нет, нажмите «Создать карточку». Для незавершённых файловых операций приложение предложит явное подтверждение восстановления, затем повторит проверку. Эти действия доступны редактору и администратору.

«Загрузить в очередь» сохраняет исходник ведомости в `resource_imports`; ресурсы создаются только после подтверждения импорта. Закрытие окна не выполняет импорт, загруженный файл остаётся в очереди. Повторный предпросмотр ничего не записывает.

Экспорт `package-export` и скачивание ZIP проверяют выбранные выпуски и оригиналы, сохраняя аудит в `<путь выбранной БД>.audit.sqlite3`. Храните этот файл вместе с БД и отдельным хранилищем аккаунтов; процессу сервера нужны права записи рядом с БД. Если аудит недоступен, ZIP не выдаётся. Безопасные файловые журналы и производный индекс `knowledge.db` могут обновляться при чтении.

В `logs/db.log` записываются серверные операции с БД. В `logs/ai.log` попадают обращения веб-приложения к нормативной базе и вызовы CLI с флагом `--agent`. Переписка с внешним ИИ хранится в его чате.

HTTP и CLI используют сервисный слой `app/itd/services` с общими правами.
Веб-актор определяется по текущей учётной записи при каждом запросе. CLI
остаётся доверенным локальным инструментом с полномочиями пользователя ОС,
которому доступны файлы БД; он не предоставляет удалённый вход. Флаг `--agent`
сохраняет прежний журнал и обозначает источник `cli-agent` с локальным
пользователем-поручителем. Прямые сервисные вызовы требуют явного актора.
Веб-сервер применяет миграции при согласованном запуске. Для CLI-записи в БД
прежней версии сначала выполните `init` с её явным `--db`; чтение не мигрирует БД.

Миграция 023 добавляет к SQL-аудиту актора, роль, источник, поручителя и результат.
Новые события сервисов не сохраняют полные запросы, результаты и персональные
данные; исторические события не переписываются. Повторное открытие списка и
повторное создание уже существующей карточки сохраняют прежние границы чтения.
Аудит ZIP остаётся в отдельном файле; существующие файлы аудита автоматически
получают поля актора при следующей выдаче. Отказы и ошибки фиксируются безопасными
метаданными в файловом журнале, без записи в читаемую деловую БД.

Все файлы локальных знаний сверяются с `app/knowledge-integrity.sha256` до
обращений HTTP/CLI к канонической базе. Отсутствующий оригинал, повреждённый PDF
или незагруженный LFS-объект приводит к ошибке. Манифест обновляют только вместе
с явно согласованным изменением базы знаний. Производный индекс по-прежнему
использует FTS5; команды, флаги и JSON-ответы сохранены. Для staging-каталогов
по явному `--root` действуют прежние проверки структуры и непустого входа.



## Состав репозитория

Публикуются исходники, миграции, определения форм и готовые шаблоны. Папки `ИТД` и `ИТД_тест`, рабочие базы, архивы выпущенных документов, журналы и локальные настройки в репозиторий не входят. При первом запуске создаётся чистая рабочая база.

## Проверка разработки

Из корня проекта выполните `.venv/bin/python app/scripts/run_tests.py`: команда
запускает `unittest discover` и frontend `npm test` (`node --test`), сохраняет
отдельные логи в `db/work/test-results` и возвращает ошибку, если любой прогон
не прошёл. Путь логов задаётся через `--log-dir`. Нужны Node.js, npm и зависимости
из `app/frontend/package-lock.json` (`npm ci` в `app/frontend`), а HTTP-тестам —
разрешённые локальные сокеты. Для отчёта покрытия установите отдельно `coverage`
и добавьте `--coverage`; зависимости работающего приложения не меняются.

Начальные правила ruff и ESLint заданы в `ruff.toml` и `eslint.config.mjs`.
Линтеры пока не включены в обязательный прогон; массовое форматирование
и автоматические исправления выполняются отдельным изменением.

Девять утверждённых контрактных проверок включены в обычный discover:
команды и флаги, 207 путей форм/шаблонов, ссылки навыков, справка без создания
БД/дерева, хеши всех знаний с отказом при повреждении PDF, формат ai.log,
документированные пути и 89 известных отсутствующих исходных бланков.
Короткий запуск: `PYTHONPATH=app .venv/bin/python -m unittest discover -s app/tests -k AgentContract -v`.


## Общий сервер и интерфейс: этап 2

Выбраны FastAPI и SQLite с WAL. Команда запуска и её параметры сохраняются;
`web` передаёт зарезервированный сокет Uvicorn. Рабочая БД располагается на
сервере, все сотрудники подключаются к одному адресу. WAL включается при
явной подготовке, обычный просмотр не меняет режим БД.

Сеансы хранятся в отдельной accounts.sqlite3 только в виде SHA-256 токенов и
переживают перезапуск в пределах прежних сроков жизни/простоя. Их схема имеет
собственную историю account_schema_migrations; пользователи и коды сохраняются.
Действующие формы сохранены с Astryx-адаптерами. Для совместимости доступны прежние маршруты
и /api/v1; новый формат ошибок v1 содержит error.code и error.message.
Для разработки установите `-r app/requirements-dev.txt` (ASGI-тесты).

В «Реестр ИД» после DOCX добавлен «Экспорт ZIP»: выбранные выпуски и связанные
приложения, без повторной генерации документов. Имя каждого выпущенного файла
сохраняется; обязательный отдельный аудит и проверки хешей действуют как раньше.
Пять обязательных UI-сценариев и ограничения ручной проверки описаны в
`db/work/manual-ui-check.md`; общий отчёт — `db/work/etap2-completion.md`.
