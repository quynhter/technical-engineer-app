# Подготовка DOCX-шаблонов

## Общая XLSX-ведомость (0.0.6)

`Ведомость оборудования и материалов.xlsx` — предоставленный пользователем
образец «пример.xlsx», сохранённый без изменения исходного файла.
Команда `statement-xlsx` загружает его обоими движками: объект подставляется
в B3, название раздела и шифр — в B4, девять колонок ресурсов — с A8.
Строки 6–7 содержат заголовки и нумерацию. Высота строк подбирается по тексту;
в выпуске закреплены только строки 1–7 вместо восьми колонок образца.
Это отдельная общая ведомость раздела, она не требует `form-register`
и не заменяет ведомости DOCX выбранного комплекта форм.

## DOCX

Для нового генератора выбрана библиотека `docxtpl`. Шаблон оформляется в Word: текст, таблицы, поля страницы, шрифты и подписи остаются в DOCX, значения подставляются из подготовленного по БД контекста.

Рабочие шаблоны распределены так:

- `СП 77.13330.2016/СП_77_А_21.docx` — подготовленная ведомость автоматизации.
- Ещё 58 форм из 12 комплектов СП, включая 16 форм из Excel, —
  [каталог форм СП](СП_ФОРМЫ.md). К каждому комплекту приложен `ПОЛЯ.md`;
  JSON полей находится в одноимённой папке `app/forms`.
- `И 1.13-07/И_1_13_07_<номер>.docx` — 25 шаблонов по всем предоставленным исходникам, включая 6а, 6б и 14а.
- `Приказ Минстроя №344_пр/МИНСТРОЙ_344_<сокращение>.docx` — пять особых актов по предоставленным формам. [Описание и подключение](%D0%9F%D1%80%D0%B8%D0%BA%D0%B0%D0%B7%20%D0%9C%D0%B8%D0%BD%D1%81%D1%82%D1%80%D0%BE%D1%8F%20%E2%84%96344_%D0%BF%D1%80/README.md).
- `РЕЕСТР_ИТД.docx` — общий реестр в корне.
- `Титульники/ТИТУЛЬНЫЙ_ЛИСТ.docx` — титулы и наклейки из TitleGenerator.
  [Поля, настройки и подключение](Титульники/README.md).

Имя файла без расширения — код `document_types.code`, на который ссылается
`acts.act_type`. Генератор рекурсивно ищет **единственный** DOCX с таким именем.
Дубликаты запрещены, даже если один находится в корне, а другой в подпапке.
Параметр `generate --templates` задаёт корень поиска. Действующие коды СП 77
и общего реестра сохранены. Старый исходный DOCX ведомости удалён по запросу;
рабочий `СП_77_А_21.docx` сохранён без изменения содержимого.

JSON полей находятся в `app/forms`; для И 1.13-07 — в одноимённой подпапке.
Пути, названия, группы регистрации и SHA-256 исходников перечислены в
[`catalog.json`](catalog.json), поля И 1.13-07 — в [`ПОЛЯ.md`](%D0%98%201.13-07/%D0%9F%D0%9E%D0%9B%D0%AF.md), поля актов №344/пр — в [отдельном каталоге](%D0%9F%D1%80%D0%B8%D0%BA%D0%B0%D0%B7%20%D0%9C%D0%B8%D0%BD%D1%81%D1%82%D1%80%D0%BE%D1%8F%20%E2%84%96344_%D0%BF%D1%80/%D0%9F%D0%9E%D0%9B%D0%AF.md).
Исходники в `misc/downloads/Исходные формы документов/И 1.13-07` не изменялись.
Регистрация форм сама по себе не создаёт документы и не назначает комплект разделу.
Комплект выбирается в разговоре с агентом и сохраняется в `projects.form_set`.

## Простые поля

Вставляйте маркер целиком, с одинаковым оформлением всех его символов:

```text
Город {{ city }}
Объект {{ object_name }}
Проект {{ project_name }}
«{{ day }}» {{ month }} {{ year }} г.
```

Имя поля не обязано совпадать с именем столбца БД. Агент хранит в JSON привязку: например, `city` берётся из города раздела, а `month` — из даты подписания акта с оформлением месяца прописью.

## Повторяющиеся строки таблицы

Для переменного количества материалов нужна таблица с заголовком и тремя служебными строками:

1. В отдельной строке таблицы: `{%tr for item in materials %}`.
2. В следующей строке — образец данных, по полям в ячейках: `{{ item.no }}`, `{{ item.spec_no }}`, `{{ item.item_name }}`, `{{ item.item_type }}`, `{{ item.serial_no }}`, `{{ item.notes }}`.
3. В отдельной следующей строке: `{%tr endfor %}`.

Первая и третья строки удаляются при генерации. Строка данных повторяется для каждого ресурса. Начальный и конечный маркер нельзя помещать в одну строку таблицы.

Порядок строк ресурсов и критерии отбора задаются данными формы, а не отдельным переписыванием DOCX для каждого раздела.

## Повторяющиеся абзацы

Для списка организаций:

```text
{%p for company in companies %}
{{ company.role }}: {{ company.name }}
{%p endfor %}
```

Каждая из трёх строк должна быть отдельным абзацем Word.

## Правила

- Сохраняйте файл в формате DOCX.
- Не разбивайте один маркер разным шрифтом, жирностью или переносом абзаца.
- Пустая строка и отсутствующее значение различаются. Неподготовленный контекст с отсутствующими переменными вызывает ошибку; режим черновика будет явно передавать отметки пропусков.
- Не создавайте в шаблоне SQL-запросы и команды. Данные собирает инструмент агента до рендеринга.
- При переходе со старой разметки `{city}` нужны новые маркеры `{{ city }}`. Рабочая копия ведомости уже преобразована; рабочий файл подготовлен ранее, а старый исходник удалён по запросу пользователя.
- У итогового документа нужно проверить внешний вид, особенно длинные названия, многострочные заводские номера и переходы таблицы между страницами.

Источник синтаксиса: [документация python-docx-template](https://docxtpl.readthedocs.io/en/stable/).

## Подписанты и проверка

В рабочей ведомости блоки подписантов используют `{{ recipient }}` и `{{ consignor }}`. Состав строки определяет JSON-поле `signatory`, а не фиксированный набор отдельных маркеров. Для другой формы агент может подготовить другое представление того же назначенного лица, включая НРС или приказ.

Шаблон ведомости проверен генерацией из SQLite и визуально на коротком примере и многостраничной таблице с длинными названиями. Заголовки таблицы повторяются, строки не разрываются между страницами, если помещаются целиком на страницу. Шаблон реестра подготовлен по согласованным колонкам, без присвоения ему номера нормативной формы.

У каждого нового шаблона нужно отдельно проверить обязательные поля и внешний вид. Готовность двух примеров не означает наличие всех остальных форм ИТД.

## Индивидуальные таблицы И 1.13-07

Данные измерений и журналов не выводятся из спецификации. Для них поддерживается
`kind: "table"` с `value` вместо `source`. Пустое значение — `null`.
Агент сохраняет заполненную таблицу в `acts.fields` через `record-update`;
строки проходят проверку обязательных ячеек, ноль сохраняется числом.
При переопределении поля таблицы сохраняются его `fields` и `required`.

```json
{
  "key": "rows_3",
  "kind": "table",
  "required": true,
  "value": [{"c1": "Участок 1", "c2": "В-1", "c3": 100, "c4": 0, "c5": 3, "c6": ""}],
  "fields": [
    {"key": "c1", "kind": "reference", "source": "item.c1", "required": true},
    {"key": "c2", "kind": "reference", "source": "item.c2", "required": true},
    {"key": "c3", "kind": "reference", "source": "item.c3", "required": true},
    {"key": "c4", "kind": "reference", "source": "item.c4", "required": true},
    {"key": "c5", "kind": "reference", "source": "item.c5", "required": true},
    {"key": "c6", "kind": "reference", "source": "item.c6"}
  ]
}
```

Это учебный пример структуры для формы 12, не результаты испытаний.
`source` и `value` одновременно запрещены. Форма 5 использует явно выбранные
`resources` и их `qty_fact`; проектное количество туда не подставляется.
Индивидуальные поля `t<таблица>_r<строка>_c<ячейка>` имеют описания в каталоге.
Стандартные роли организаций и подписантов этих форм: `installer`, `customer`,
`general_contractor`, `builder`, `commissioner`, `foreman`, `inspector`, `worker`.
Их назначает агент по фактическим участникам, а не по порядку записей БД.

Даты акта готовности и ведомости недоделок — отдельные даты соответствующих
документов, а не дата подписания текущего акта. Значения дат передаются как
`ГГГГ-ММ-ДД`. Год на обложке указывается отдельно.

В исходных бланках есть готовые утверждения о выполненных работах,
соответствии и результатах. Перед выпуском агент сверяет их с фактическими
данными; наличие бланка и успешная генерация не подтверждают эти факты.
Заключения и сведения об отсутствии дефектов нельзя выдумывать.

Форма 1 сохраняет три раздела исходной ведомости; её номера и количество листов
заполняются отдельно. Ручные подписи остаются пустыми. Ошибочный заголовок
протокола прогрева удалён только из рабочего шаблона формы 18.
Каждый выпуск требует проверки на фактических данных: произвольная длина
названий, объём таблиц и индивидуальные дополнения могут менять число страниц.


### Связи с карточками без изменения бланка

`app/forms/bindings.json` задаёт явные источники для пустых полей каталога.
Нормализация `apply_form_defaults` общая для ввода, предпросмотра и DOCX.
Исходные регистрации и индивидуальный заполненный текст сохраняются.
Карта использует роли из участников, `object`, `project`, `project_documentation`
и `field_values` для повторения уже разрешённых полей. Варианты роли, прямо
допущенные бланком, помечены `role_slot`/`role_options` и выбираются пользователем.
Проверка всех связей: `PYTHONPATH=app .venv/bin/python app/scripts/audit_relationships.py`.
Обновление подробной карты: та же команда с `--write-map`. Результат — [MAP.md](../../MAP.md).

Для новых полей можно использовать осмысленные источники в JSON формы. Например, `Object.City` берёт город объекта, `Project.ShortName` берёт обозначение раздела, `Project.Name` берёт полное название, а `Project.Cipher` берёт шифр РД. Подставляйте в DOCX ключ поля, заданный в JSON. Старые источники остаются действующими.

`Organisation.42.Name` и `Organisation.42.Inn` берут реквизиты организации с ID 42 из участников объекта. `Representative.17.Position` и `Representative.17.Organisation.ShortName` берут должность представителя и сокращённое название его организации. Суффикс `~default=КОД_РОЛИ` в источнике позволяет подставить участника по роли, если конкретный ID не указан или отсутствует. Например, `Representative.Id.Position~default=builder_control` берёт должность выбранного представителя строительного контроля подрядчика.
