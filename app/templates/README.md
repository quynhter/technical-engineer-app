# Создание DOCX-шаблона

Все 91 поставляемая форма используют один объектный контракт. Имена свойств —
английские, значения и подписи формы — русские. Список свойств конкретной формы:
[справочник всех форм](TEMPLATE_FIELDS.md).

## Объекты и свойства

| Объект | Примеры свойств |
| --- | --- |
| `object` | `name`, `address`, `city`, `construction_type` |
| `project` | `name`, `section_code`, `code`, `city`, `documentation` |
| `document` | `number`, `code`, `date` |
| `document.date` | `text`, `iso`, `day`, `month`, `month_number`, `year` |
| `recipient`, `consignor` | `position`, `last_name`, `first_name`, `middle_name`, `fio`, `fio_short`, `organisation`, `authority`, `nrs_id` |
| `organisations.customer` | `name`, `short_name`, `full_name`, `inn`, `ogrn`, `address`, `phone`, `sro_info`, `role`, `role_key` |
| `representatives.customer_control` | Те же свойства представителя, что у `recipient` |
| `companies` | Список назначенных организаций; каждый элемент имеет свойства Organisation |
| `form` | Только индивидуальные сведения выбранной формы: измерения, результаты, даты работ, приложения |

`organisation` внутри представителя — вложенный объект, а не текстовая строка.
`{{ recipient.organisation }}` печатает его короткое или полное название;
`{{ recipient.organisation.inn }}` печатает ИНН. Написание `organisation` одинаково
во всех шаблонах. Названия ролей не переводятся в именах свойств:
`company.role` — «Заказчик», `company.role_key` — `customer`.

`recipient` и `consignor` обозначают выбранных для документа получателя и
отправителя. Остальные роли доступны через `representatives.<role_key>` и
`organisations.<role_key>`, например `representatives.builder_control.position`.
Отдельное имя `company` появляется внутри цикла, показанного ниже.

## Текст в Word

Готовый учебный образец: [STARTER.docx](../docs/templates/STARTER.docx) и
[его поля JSON](../docs/templates/STARTER.fields.json). Скопируйте оба файла,
задайте свой код и замените текст бланка; маркеры можно оформлять прямо в Word.

Вставляйте каждый маркер целиком, с одинаковым оформлением его символов:

```jinja
Город {{ object.city }}
Объект {{ object.name }}, {{ object.address }}
Раздел {{ project.name }}, шифр {{ project.code }}
Документ № {{ document.number }} от {{ document.date }}
«{{ document.date.day }}» {{ document.date.month }} {{ document.date.year }} г.
Принял: {{ recipient.position }} {{ recipient.organisation.short_name }}
{{ recipient.last_name }} {{ recipient.first_name }} {{ recipient.middle_name }}
```

Можно использовать готовое представление `{{ recipient }}` или `{{ recipient.text }}`,
либо составить строку самостоятельно из свойств. Эти варианты работают с одним
выбранным лицом. Если в старой карточке внесено только ФИО целиком, `fio`
сохранится, а отдельные части имени следует заполнить в карточке представителя;
генератор не угадывает фамилию и составное имя.

## Списки организаций

Каждая из трёх строк — отдельный абзац Word:

```jinja
{%p for company in companies %}
{{ company.role }}: {{ company.name }}, ИНН {{ company.inn }}
{%p endfor %}
```

Для одной конкретной организации цикл не нужен:
`{{ organisations.customer.full_name }}`.

## Строки таблиц

Для примера `СП_77_А_19_УЧАСТОК` таблица имеет шапку и три служебные строки:

1. В отдельной строке: `{%tr for measurement in form.fibre_measurements %}`.
2. В строке данных по ячейкам: `{{ measurement.fibre_number }}`,
   `{{ measurement.power_ab_input }}`, `{{ measurement.power_ab_output }}`,
   `{{ measurement.power_ba_input }}`, `{{ measurement.power_ba_output }}`,
   `{{ measurement.attenuation_db }}`, `{{ measurement.measured_on }}`.
3. В следующей отдельной строке: `{%tr endfor %}`.

Строки начала и конца цикла удаляются при генерации, строка данных повторяется.
Имена колонок и списка берите из справочника своей формы. У одной и той же
поставляемой формы они одинаковы при работе через веб-интерфейс и CLI.

## Собственное поле

Объекты, организации и выбранные представители собираются из карточек.
Индивидуальное поле объявляется в JSON формы с явным `template_path`:

```json
[
  {
    "key": "recipient",
    "label": "Получатель",
    "kind": "signatory",
    "role": "recipient",
    "presentation": "position_org_fio",
    "required": true,
    "template_path": "recipient.text"
  },
  {
    "key": "test_pressure",
    "label": "Испытательное давление, МПа",
    "kind": "literal",
    "value_type": "number",
    "required": true,
    "value": null,
    "template_path": "form.test.pressure"
  }
]
```

В DOCX: `Давление {{ form.test.pressure }} МПа`. `key` — идентификатор значения
карточки; `template_path` — свойство, которым пользуется автор DOCX. Оно не зависит
от номера таблицы, строки или ячейки. Для обязательного отдельного реквизита можно
объявить reference с `source: "signatories.recipient.last_name"`,
`template_path: "recipient.last_name"`, `required: true`.

Для своего повторяемого списка используйте `kind: "table"`, массив `value` и
`fields` с источниками `item.<column>`. У каждой колонки `template_path` задаётся
относительно строки, например `pressure`; у списка — `form.measurements`.
Значения дат задаются как `ГГГГ-ММ-ДД`. Даты работ и испытаний не подменяются датой
подписания документа.

В поставляемых бланках группы дня, месяца и года описаны в
`app/forms/date_groups.json`. `apply_form_defaults` оставляет одно календарное
поле и вычисляет остальные части через `date_inputs.<key>` — исходную ISO-дату
ручного поля, до применения печатного формата. Ключи и пути DOCX сохраняются.
В СП_77_А_5 группа читает `project.smr_start` / `project.smr_end`; введённая вручную
дата имеет приоритет. Прежние заполненные части даты сохраняются как текст с
понятными подписями. Другие даты, в том числе журналов, договоров и приказов,
не связываются с периодом СМР по сходству названия.

В версии документа кнопка «Добавить → Иное лицо» позволяет выбрать до трёх
представителей из участников строительства. Выбранные лица печатаются в конце
DOCX с реквизитами и местом для подписи по сетке подписантов исходного шаблона;
невыбранные лица не добавляются. Дополнительные поля бланка для этого не нужны.

## Проверка и подключение

1. Сохраните DOCX под уникальным кодом формы и JSON полей с тем же кодом.
   Для поставляемой библиотеки добавьте запись в `catalog.json`. Для отдельной
   папки шаблонов передавайте её абсолютный путь через `generate --templates`.
2. Посмотрите общий контракт без открытия БД:
   `PYTHONPATH=app .venv/bin/python -m itd --agent template-schema`.
   Для конкретной формы добавьте `--type СП_77_А_21`.
3. Зарегистрируйте форму на выбранной тестовой БД штатной командой
   `--agent form-register`, создайте тестовый документ и выполните `--agent generate`.
   Путь тестовой БД передавайте явно через `--db`.
4. Проверьте короткие и длинные значения, пустые поля, многостраничную таблицу,
   подписи и колонтитулы. Таблицам задайте фиксированную ширину; заголовки,
   обычные реквизиты и основной текст верстайте абзацами. Подписанные документы
   и архивные выпуски не переписываются.
5. Подключайте проверенную форму в рабочей БД после выбора БД и объекта.

Текущие значения объектов выбранного документа можно посмотреть командой
`--agent act-context --act-id ID --objects`, передав `--db` с путём тестовой БД.

Опечатка в свойстве вызывает ошибку, необработанные маркеры не выпускаются.
Пустые обязательные данные блокируют окончательный выпуск. В DOCX не нужны SQL,
Python-код, русские имена переменных или блоки `set`.

Технические ключи старых карточек сохранены в JSON и
`app/forms/template_contracts.json`. Они нужны для чтения существующих БД;
переименовывать их и заново регистрировать 91 форму для работы новых шаблонов
не требуется. Снимок прежних рабочих файлов с SHA-256 находится в
`app/docs/template-layout/before-object-contract.zip`; нормативное происхождение
хранится отдельно в [каталоге](catalog.json).

Открытый [пример АОГРО ИД-Просто](https://id-prosto.ru/examples/344-pr/new-aogro)
используется как образец расположения реквизитов и заполнения. Его учебные данные
не подставляются в рабочие документы. Применимость формы и фактические утверждения
проверяются отдельно от технической генерации.
