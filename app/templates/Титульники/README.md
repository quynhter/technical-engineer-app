# Титульные листы и наклейки

Функции перенесены из пользовательского Rust-проекта TitleGenerator.
Оригинал `assets/template.docx` сохранён без изменения в
`misc/downloads/Исходные формы документов/Титульники/template.docx`.
Его SHA-256 записан в общем `catalog.json`. Адаптация воспроизводится скриптом
`app/scripts/prepare_title_template.py --source … --output …` в новый файл.

Форма `ТИТУЛЬНЫЙ_ЛИСТ` общая для комплектов СП 77 и И 1.13-07. Она не назначает
комплект раздела и не устанавливает нормативную обязательность титула.
Агент создаёт её через `title-add --project-id … --data …`, затем использует
обычные `act-context`, `generate`, `release-verify` и `package-export`.
Настройки сохраняются в `acts.fields`, поэтому повторный выпуск воспроизводим.
Существующая регистрация формы с другими настройками не заменяется молча.

На каждую пару «экземпляр × том» идут титульный лист и страница с тремя
наклейками. Порядок: все тома первого экземпляра, затем все тома второго.
Первый экземпляр — «Оригинал», следующие — «2 экз.», «3 экз.» и далее.
При единственном томе строка «Том … из …» пустая.
`labels: false` исключает страницу наклеек. Высота наклеек растёт по содержимому;
размеры отличаются от фиксированных фигур оригинала. Названия не сокращаются.
При особо длинных реквизитах число печатных страниц может увеличиться:
перед выдачей обязательно проверить вёрстку. `sheets_count` вводится отдельно.

Объект (`object.name`), раздел, шифр и город разрешаются из текущей БД при
каждом выпуске. Участники выводятся по полным наименованиям организаций.
Стандартные ключи назначений: `Заказчик`, `Технический_заказчик`, `Генподрядчик`,
`Подрядчик`. Для других уже согласованных ключей передайте явное сопоставление
`roles`, например `{"sub_contractor": "builder"}`. Не создавайте назначения,
исходя только из подписи договора. Отсутствующие участники по умолчанию
необязательны и оставляются пустыми; обязательность задаётся полями формы.

Год задаётся явно (1900–2100); пропуск отмечается в черновике и блокирует финал.
Количество экземпляров и томов — целые 1–50. Поддерживаются `Arial` и
`GOST type B` (для последнего шрифт должен быть установлен в среде просмотра).
Настройки по умолчанию: один экземпляр, один том, Arial, наклейки включены.

Старые конфигурации JSON читаются напрямую: `object`, `project`, `cifr`,
`client`, `tech_client`, `gen_contractor`, `sub_contractor`, `city`, `year`,
`copies`, `volumes`, `font_index` (0 — Arial, 1 — GOST type B).
Значения целых чисел, сохранённые Rust как `2.0`, принимаются.
Непустые деловые значения из конфигурации сверяются с БД дословно;
расхождения блокируют создание и требуют согласования. Пустые старые поля
не стирают текущие сведения. Неизвестные настройки отклоняются.
`title-config --act-id … --output …` сохраняет текущую конфигурацию в новый JSON,
включая сопоставление ролей. Старый файл не перезаписывается.

Титульник использует существующую таблицу документов `acts` и группу `act`:
автоматическая папка — `03_Акты/Черновики` или `03_Акты/Выдача`.
Внутренний номер выделяется общим счётчиком, но не печатается на титуле
и в его строке реестра. Шаблон не содержит ссылки на `act.act_num`.
Для повторного выпуска используйте тот же `act_id`, не создавайте новый
титульник только ради обновления реквизитов. Новые миграции не требуются.

Настройки можно менять штатным `record-update` по точному ID с `--expected`:
поле `fields` передаётся целиком, с сохранением остальных настроек.
После изменения требуется новый `generate`. Ручное редактирование выходного
DOCX не заменяет изменения в БД.
