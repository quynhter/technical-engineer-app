# Работа через инструменты приложения

## Контекст и команды

Работай из корня репозитория. Сверяй текущий синтаксис через `--help`,
а JSON операций без подробной справки — по их обработчикам в
[manual.py](../../../app/itd/manual.py), [workspace.py](../../../app/itd/workspace.py),
[workflow.py](../../../app/itd/workflow.py) и
[document_versions.py](../../../app/itd/document_versions.py).
Связи и ограничения смотри в [MAP.md](../../../MAP.md). Не придумывай параметры
или поля и не переноси ID из другой БД.

После установления путей можно использовать оболочку над CLI:

```bash
# ITD_TASK_DB и ITD_TASK_ROOT — подтверждённые абсолютные пути текущей задачи.
itd_task() {
  PYTHONPATH=app .venv/bin/python -m itd --agent \
    --db "$ITD_TASK_DB" --itd-root "$ITD_TASK_ROOT" "$@"
}
itd_task --help
itd_task list objects
itd_task list projects
itd_task project-context --project-id "$ITD_TASK_PROJECT_ID"
```

Задавай переменные из проверенного контекста, а не из примеров или старой задачи.
Не меняй настройки сервиса ради удобства CLI. Для путей вне проекта используй
полные пути; имя объекта и отдельный адрес сохраняй в соответствующих полях.

| Действие | Штатные точки входа |
|---|---|
| Инвентаризация, контроль до/после | `list`, `project-context`, `workflow-context`, `project-check`, `package-matrix`, `fact-summary` |
| Резервная копия SQLite | `backup --output`; архив оригиналов копируется отдельно |
| Чтение источников, архив, связи | `read-document`, `file-add`, `file-link` |
| Импорт и сравнение редакций | `workspace-action`: `resource-import-stage`, `resource-import-preview`, `resource-import-commit`; `spec-import`, `spec-compare` |
| Участники и реквизиты | `organization-add`, `signatory-add`, `assign`, `record-update --expected` |
| Приходы и карточка ресурса | `workspace-action`: `context`, `resource-card-save`, `supply-add`, `supply-set` |
| Журналы и входной контроль | `workspace-action`: `entry-save`, `special-journal-save`; `quality-review-add`; групповая форма ЖВК в веб-интерфейсе |
| Подготовка документа и его состава | `workspace-action`: `form-connect`; `act-add`, `act-resources`, `act-schemes`, `act-facts`; `workspace-action`: `act-entries`, `act-composition` |
| Согласованный состав комплекта | `requirement-add`, `requirement-set`; контекст раздела через `record-update` с `--expected` |
| Подписанты и карточка версии | `workspace-action`: `act-signatories`, `document-version-ensure`, `document-version-save` |
| Проверка и выпуск | `act-context`, `act-review`, `generate`, `statement-xlsx` |
| История и выдача | `release-list`, `release-verify`, `release-select`, `release-unselect`, `release-recover`, `release-publish`, `release-reconcile`, `package-export` |
| Учёт сдачи и замечаний | `delivery-add`, `delivery-set`, `remark-add`, `remark-resolve` |

`workspace-action` получает `--project-id`, `--action` и путь `--data` к JSON.
Для изменяемых записей перечитай значения и передай нужные `expected`/`revision`.
Не убирай эти проверки при конфликте: сверь изменения и повтори осознанно.
Рабочие JSON и контрольные результаты сохраняй в отдельном каталоге задачи
под `db/work/`, не в навыке и не в общем файле, который может использовать
другая операция. Не выполняй пакетные повторы вслепую после частичного успеха.

При изменении `projects.agent_context` сначала прочитай существующий объект
и объедини с ним новые решения; не затирай чужие сведения. Для индивидуальных
полей акта сохраняй определения таблиц, `template_path`, источники и форматы.
В `expected` передавай фактическое хранимое значение соответствующего поля,
а не произвольно пересобранный JSON; карточка версии использует свой контракт.

## Учёт работ и материалов

До записи монтажа проверь участников и исполнителей раздела 1 ОЖР, их
организации, полномочия и периоды участия. Назначения организации и подписанта
по роли проверяются отдельно. Для нескольких допустимых представителей выбирай
по фактическому участию, а не первый элемент списка.

Сохраняй работу через `entry-save`: дату, содержание, место, ответственного,
индивидуальные поля вида работ и использованные ресурсы. `materials` создаёт
связанные факты монтажа автоматически; не добавляй тот же прирост вторично
через `fact-add`. Итог `qty_fact` сверяй с подтверждёнными приростами, но не
перезаписывай его автоматически без проверки полноты и основания.

Сверь приходы, контроль и расход по каждой позиции и единице. Не требуй
нулевого остатка там, где по задаче допускается запас или частичный монтаж.
Отрицательный остаток, неизвестная поставка и превышение проектного количества
требуют разбора; согласованные дополнительные материалы сохраняй с основанием,
не подменяя проектные количества. Отзыв дублирующего прихода сохраняет историю
и требует проверки связанных работ и контроля.

Для входного контроля связывай ресурс, поставку, оригинал, результат контроля
и результат сверки документа качества. Не списывай материал повторно через
самостоятельное выделение в акт, если расход уже внесён работой.

Сначала строй хронологию по фактическим зависимостям: готовность и разрешения,
приход и контроль, требуемые проверки до монтажа, монтаж, освидетельствование
до закрытия, испытания, наладка, передача. Журналы могут расширять даты объекта
и СМР; перечитывай их после сохранения, отдельно сверяя период ПНР. Уважай
требуемое приложением подтверждение переноса начала периода.

## Документы и версии

Связывай акт с относящимися к нему ресурсами, фактами, схемами и файлами.
Не приписывай передачному акту или предмонтажному протоколу будущие факты
монтажа только для устранения предупреждения. Номер документа бери из записи
акта после создания: внутренний ID и номер счётчика не взаимозаменяемы.

Проверяй все выбранные роли, включая дополнительные `other_1`–`other_3`,
в карточке, печатном файле и текущей версии. Роль, организация и полномочия
должны соответствовать конкретному документу. Добавление лица в справочник
или на объект не означает автоматического включения в каждый акт.

После изменения состава или исходников перечитай карточку версии и `act-context`.
Если источники изменились, повторно проверь их перед `sources-review`.
Выпущенный файл не редактируй напрямую: используй следующую версию, повторную
проверку и штатный выпуск. Новая версия не наследует факт подписания нового
файла от старого.

При сбое сначала проверь БД, выпуски, файлы и незавершённые операции.
`release-recover` продолжает операцию переноса, `release-publish` — публикацию
существующего выпуска; это не повод повторно создавать акт. Результат операции
и точки продолжения записывай так, чтобы следующий запуск мог продолжить задачу.
